# 01 选题与需求分析

## 1.1 选题

**主 App：B1 校园二手交易（无支付）**
**伴生模块：P1 桌面小组件**

B1 的强制技术点是「网络 + 图片处理 + 权限 + 云存储」，正好覆盖课程要求的三大硬能力中的两项
（真实 API 网络请求、相机/定位等设备能力），并且天然包含图片上传这一工程难点，可做的深度足够，
不会退化成简单的增删改查。

## 1.2 为什么不做支付

课程明确「无支付」。这不是砍功能，而是把精力集中到二手交易里真正难的部分：
**商品信息质量（图片 + 定价）** 和 **信息匹配（搜索 + 距离）**。
支付需要接第三方 SDK、涉及资金安全与合规，对课程目标（Android 技术深度）没有增益。

## 1.3 目标用户与场景

用户是**在校学生**：预算有限、活动范围集中在校园、交易以当面自提为主、发布频率低但决策依赖图片与价格。

四个核心场景（后面的功能清单都从这里来）：

| 场景 | 用户动作 | 对 App 的要求 |
| --- | --- | --- |
| S1 想卖东西 | 拍几张照、写标题、**不知道该卖多少钱** | 发布流程要短；要有定价参考；图片要清楚又不能太大 |
| S2 想买东西 | 刷列表、按分类看、搜索关键词、看详情 | 列表要有「性价比」信号；详情信息完整；图片加载要快 |
| S3 离得近的优先 | 想知道「谁离我最近，能不能马上拿到」 | 位置权限 + 距离排序；拒绝权限也不能崩 |
| S4 先收藏再决定 | 收藏几个，回来看 | 收藏持久化；断网也能看收藏与缓存 |

其中 **S1 的「不知道卖多少钱」** 是真实痛点：学生第一次卖东西，定价普遍偏高（卖不掉）或偏低（吃亏）。
这就是「智能定价助手」的来源——它不是凭空加的功能，而是从场景里长出来的。

## 1.4 与现有方案的差异

| 方案 | 问题 |
| --- | --- |
| 微信群/QQ 群发消息 | 无结构、不可搜索、消息被刷走 |
| 闲鱼/转转 | 面向社会，同城范围过大，学生用不上「校园内自提」；且强依赖平台账号 |
| 校园墙/表白墙代发 | 人工转发，价格与成色靠描述，无图片压缩与统一字段 |

本项目的定位：**信息结构化的校园内二手流转工具**，只做「发现 → 沟通 → 当面交易」，
不做支付、不做物流、不做信用体系。

## 1.5 个性化差异（防抄袭要求）

同题多人时按学号分配差异化功能。本项目采用的组合是
**2 个必做特色功能 + 1 个自选功能**：

| 类型 | 功能 | 对应课程要求 |
| --- | --- | --- |
| 必做 ① | 智能定价助手（估价算法 + 定价合理性评分 + 捡漏标记） | 「自定义业务逻辑模块」 |
| 必做 ② | 图片处理流水线（多图 → 压缩 → EXIF 脱敏 → 带进度上传 → 重试） | B1 的「图片处理」，同时是工程难点 |
| 选做 | 附近好物（定位 + 距离排序 + 权限拒绝降级） | 「权限申请与降级处理」+ 设备能力 |

三个功能互相咬合：图片质量影响定价判断，定价结果影响列表排序信号，距离又影响「值不值得跑一趟」。
不是三个互不相干的 demo 拼在一起。

## 1.6 非目标（明确不做）

- 不做支付、不做订单、不做物流；
- 不做即时聊天（留言板异步即可）；
- 不做用户信用/评价体系；
- 不做多端同步冲突合并（伴生模块只读主 App 数据）。

写清楚「不做什么」同样是需求分析的一部分——它保证了两个月的开发周期能收敛。
